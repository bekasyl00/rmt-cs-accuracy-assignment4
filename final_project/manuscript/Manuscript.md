# Accuracy of AI Answers on Established and Recent Software Features

Bekasyl Zhaksylyk, Zere Amantai and Mereke Myrzakhan

Astana IT University, Astana, Kazakhstan | SE-2418

## Abstract

Technical assistants can give fluent explanations that misstate software versions. This study compares factual accuracy on established concepts and recent features and explores documentation retrieval for a local code model. Forty English questions formed twenty task- and ecosystem-matched pairs across Python, PostgreSQL, TypeScript, Node.js and Git. Established concepts were documented before 2020; selected recent features first appeared in 2025. Three archived interface conditions produced 120 answers under a prescribed no-search instruction. Scoring required three source-backed checkpoints and no material additional error. Overall, 101/120 answers were fully correct and 344/360 checkpoints were satisfied. Established-minus-recent accuracy gaps were 25, 10 and 30 percentage points for the GPT, Sonnet and Gemini conditions. None was statistically significant after Holm correction (adjusted p = 0.0938, 0.2500 and 0.0938). A separate exploratory experiment reused the bank: keyword extraction and Qwen without documents each scored 4/40, while Qwen with BM25-retrieved passages scored 6/40. This five-point improvement was not statistically established. The benchmark provides inspectable version-specific questions, judgments and calculations. Retrieval helped one module-identification example but preserved a string-enum error, illustrating that source access does not guarantee correctness. Its findings support checking technical claims against authoritative documentation, while limited sampling, unverified backend identities and AI-assisted ratings constrain generalization.

Keywords: factual reliability; version awareness; documentation retrieval; paired evaluation; code assistants

## 1 Introduction

Large language models (LLMs) are now common interfaces for explaining programming behavior, clarifying framework features, and assisting software developers with implementation choices. A student may ask an assistant how a Python feature behaves; a developer may rely on it for a PostgreSQL configuration, TypeScript type error, Node.js runtime change, or Git operation. These uses are attractive because the assistant produces a fluent, task-specific explanation quickly. Yet fluency does not establish whether each technical claim matches a particular software release. Answers that look plausible can omit a prerequisite, confuse an old interface with a newer one, or invent an available option. Such inaccuracies matter especially when the user does not already possess the expertise required to detect them. Empirical work on Stack Overflow answers has documented this problem in developer-facing explanations [1], while broader factuality studies show why generated claims should be evaluated against evidence instead of presentation quality [2,3].
Technical knowledge is also time-sensitive in a distinctive way. Stable concepts such as Python scoping rules or established Git semantics are described in longstanding references. By contrast, a software feature released in 2025 can have documentation that differs from tutorials, earlier previews, and an assistant's internalized examples. Version constraints are therefore part of the factual question, not an optional detail. Research on knowledge frequency suggests that limited exposure to relevant documents can reduce factual-question performance [4]. Work on deprecated API usage shows that library evolution poses practical problems for code generation [5]. Neither result, however, demonstrates that release recency alone causes a decrease in explanatory accuracy: difficulty, documentation quality, question phrasing, and model access to sources may also affect the outcome.
The broader evaluation literature provides complementary reasons to test this issue explicitly. Dynamic factual benchmarks such as FreshQA consider changing world facts and search-assisted answering [6]. TruthfulQA and HaluEval analyze truthfulness and unsupported content across heterogeneous domains [3,7]. In programming, functional benchmarks and repository-level tasks assess whether generated code passes tests or resolves a software issue [8,9]. Those outcomes are important, but they are not interchangeable with the correctness of a short explanation of a named, version-specific software feature. A concise answer can correctly describe two properties yet omit the third required condition, or satisfy all requested checkpoints while adding a misleading assertion. A metric based solely on accepted code, answer similarity, or a general preference judgment may not expose that difference.
This study addresses that narrower use case with a small, auditable comparative benchmark titled Accuracy of AI Answers on Established and Recent Software Features. We ask: How does the factual accuracy of answers to established computer science concepts compare with answers to recently released software features when selected chat conditions are instructed to use existing knowledge without external search? A supplementary question asks whether retrieving official documentation improves a local Qwen-based answer on the same questions. The supplementary comparison does not change the original no-search research question and is interpreted separately.
We evaluate forty English-language applied questions from five ecosystems: Python, PostgreSQL, TypeScript, Node.js, and Git. Twenty questions concern concepts documented before 2020; twenty concern software features within a 2025–2026 eligibility window, all of which actually first appeared in 2025. The instrument contains twenty pairs matched by ecosystem and type of task, not experimentally certified as equally difficult. Each answer is assessed against three binary, source-backed checkpoints using the relevant official documentation and software version. Whole-answer correctness additionally requires the absence of a material factual error. Partial, incorrect, abstaining, and missing answers are distinguished instead of silently combined. The original archive contains 120 responses: forty under each of three student-recorded interface conditions for ChatGPT, Claude, and Gemini. Their stored model labels are not independently confirmed backend identifiers. External search, retrieval, and code execution were prohibited in the prescribed prompt, but actual client tool states were not independently observed.
To make the interpretation concrete, the archived study recorded 101 fully correct answers out of 120, alongside 344 successful checkpoints out of 360. The observed established-topic accuracy exceeded the recent-topic accuracy in each original condition, but the three Holm-adjusted paired tests did not reach the exploratory 0.05 threshold. These are observations on a deliberately constructed bank, not estimates of all possible software questions or claims that recentness caused individual errors. A second experiment used the unchanged forty-item bank, comparing keyword extraction, Qwen2.5-Coder-3B-Instruct without documents, and a BM25-document-augmented variant. As the bank was already known before that extension, it cannot be called an unseen test set. The additional experiment helps illustrate retrieval limitations rather than establishing a general gain from retrieval-augmented generation.
Our contribution is therefore methodological and empirical rather than a new general-purpose model. First, we provide a balanced, task-paired, version-specific question bank spanning five widely used ecosystems, with dated primary sources and explicit checkpoints. Second, we report both complete-answer accuracy and checkpoint-level credit, allowing readers to distinguish omission from fully reliable explanations. Third, we preserve individual outputs and the scoring rationale and calculate transparent paired comparisons rather than relying only on a pooled leaderboard. Fourth, we provide a bounded additional test of official-document retrieval using a local model under reproducible settings. These contributions are modest but independently inspectable, which is valuable for assessing technical assistants where a convincing answer may still be wrong.
The rest of the article synthesizes relevant research on factuality, changing knowledge, software benchmarks, and retrieval in Section 2. Section 3 describes the question bank, archived conditions, supplementary baselines, source-backed rubric, and analysis. Section 4 reports the original and additional results, including uncertainty and scoring sensitivity. Section 5 discusses interpretation and threats to validity, and Section 6 concludes with implications for evidence-based use of AI assistance in software engineering.

## 2 Related Work

Research closest to this study spans four connected areas: factual reliability of generated explanations, temporal and long-tail knowledge, evaluation in software engineering, and retrieval-based support. These literatures measure different failure modes. Their results motivate our design, but percentages from their benchmarks should not be treated as directly comparable with the accuracy of forty version-bound technical explanations.
Factuality and claim-level evaluation. Work on TruthfulQA demonstrated that apparently reasonable language-model outputs can reproduce common misconceptions [3], while HaluEval assembled human-annotated material for studying hallucination recognition [7]. These studies address broad truthfulness, rather than behavior of named software features at particular releases. FActScore decomposes longer generations into atomic facts and evaluates factual support [2]; its key methodological lesson is that the apparent coherence of an answer need not imply support for each assertion. SelfCheckGPT instead uses consistency across samples to detect potential hallucinations without external retrieval [10]. In developer support, Kabir and colleagues examined ChatGPT answers to Stack Overflow questions and found that answer quality and user ability to recognize errors deserve separate attention [1]. Our binary checkpoints borrow the principle of individually assessable factual requirements but add a strict whole-answer rule: satisfying all requested facts is insufficient if an answer introduces an additional material error.
Judging generated text is itself a methodological issue. G-Eval proposed LLM-based scoring and highlighted the potential for judges to prefer machine-generated language [11]. Research assessing generated summaries also shows the consequences of reference quality and evaluation design [12]. Such literature supports transparent, explicit scoring criteria over an unqualified model preference score. The present benchmark uses source-backed checkpoints and records explanations for decisions; nevertheless, its ratings were AI-assisted, and the team has not measured independent human inter-rater agreement. This limitation prevents treating its scores as the output of an independently validated human annotation protocol. Fine-grained rubric transparency helps auditing but does not remove judge-related bias.
Knowledge frequency, recency, and moving ground truth. Kandpal et al. linked factual-question performance with the availability of relevant material in pretraining [4]. Importantly, rare knowledge and recently published knowledge are not synonymous. A well-documented new feature may be easier than an obscure older one, while a long-established corner case can remain difficult. FreshLLMs introduced FreshQA for changing facts and examined search augmentation [6]. The central relevance here is that date-sensitive factual questions require a reference tied to the time of evaluation. Our study applies that concern to concrete software releases: an answer about an implementation feature must be judged against the specified version, and a newer version name alone does not make a feature newly introduced. Since the study did not control training cutoffs or model exposure to release notes, an observed group difference cannot be assigned specifically to knowledge freshness.
Programming and software engineering benchmarks. HumanEval evaluates generated functions through functional tests [9], and SWE-bench extends evaluation to real GitHub maintenance issues [8]. Both make correctness observable by software execution, but neither primarily evaluates three-part prose explanations on a balanced established-versus-recent question bank. Controlled effort-estimation research also illustrates that software tasks require task-specific outcomes rather than generic ratings [13]. Tosi studied generated code quality using test suites and other metrics [14]; Christakis and Drikakis proposed multiple dimensions of code-generation evaluation, including consistency and efficiency [15]. Wang et al. examined deprecated APIs in code completion and provide a close example of software knowledge becoming obsolete as libraries evolve [5]. For educational and developer interactions, Taneski et al. examined how query types affect programming assistance [16]. Cheng et al. tested structured evaluation of UML modeling across model and prompting conditions [17], and Batsakis et al. compared model answers with a model-checking ground truth [18]. Together these papers make the case for domain-specific references and explicit measurement, while also showing why execution-oriented correctness should not simply be interpreted as factual explanation accuracy.
Documentation, attribution, and retrieval. The retrieval-augmented generation literature [19] motivates supplying external evidence when internal model knowledge may be outdated. RARR uses research and revision to provide support for generated claims [20], while ALCE assesses generated text alongside the relevance and correctness of citations [21]. Self-ask research shows that breaking down questions and invoking external search can help some multi-hop tasks [22]. Still, retrieving text is not identical to answering correctly: a retriever may return irrelevant fragments, and a generator may omit important context even when it has been retrieved. Lost in the Middle documents the sensitivity of models to where useful evidence appears in a long context [23]. The present supplementary comparison therefore separates a keyword-extraction baseline, a local Qwen model without retrieved text, and the same local model with three BM25-ranked official-document chunks. Its narrow question is whether this particular retrieval pipeline helps on the archived instrument—not whether all RAG systems are superior to all closed assistants.
The nearest examples also reveal what must be controlled and what cannot be inferred. Electronics papers comparing multiple LLMs on model checking, customizable judge workflows, and backend code quality [18,24,25] resemble our concern with reproducible cross-model evaluation but target other outcomes. Moreover, our supplementary Qwen test uses one deterministic pass and a previously inspected question bank, so it is properly labelled an exploratory extension rather than a confirmatory generalization.
Table 1 compares the closest studies according to the kind of evidence they collect. The studies differ materially in domain, reference standard, and unit of analysis: Stack Overflow explanations versus changing world facts versus deprecated APIs versus generated code or model-checking problems. None of those inspected designs, individually, provides the same paired five-ecosystem comparison of established concepts and 2025 software features with explicit three-part answers, version-specific official keys, and a separate documentation-retrieval extension. This is a bounded gap relative to the literature reviewed here, not a claim that no similar benchmark exists anywhere.
Our main research question is consequently descriptive: for these selected questions and recorded interface conditions, how much complete-answer accuracy differs between the two age-defined groups. Pairing by task reduces obvious structural imbalance, but does not equalize intrinsic difficulty, training coverage, or the probability that a fact is present in documentation. The results also should not be used to rank underlying backend models, since identities, compute budgets, and client settings were not independently verified. The benchmark contributes by making these constraints visible while providing a verifiable account of factual technical answers under prescribed no-search conditions.

## 3 Materials and Methods

### 3.1 Study design and research questions

We conducted a quantitative comparative study of factual correctness in English answers to version-specific computer science questions. The primary research question asked how accuracy differs between established concepts and recent software features across three recorded AI conditions instructed to answer without external search. The study combines an archived comparison of 120 responses with a supplementary comparison of 120 outputs from keyword extraction, a local coding model and retrieval-augmented generation (RAG). The supplement asks whether retrieved official documentation improves the local model's full-answer correctness on the same question bank. The contribution is a source-linked comparison with inspectable judgments and reproducible calculations.

The primary directional hypothesis was that established-topic accuracy exceeds recent-topic accuracy within each recorded condition. Its null permits equality or a recent-topic advantage. The supplementary hypothesis anticipated higher overall correctness with retrieval than without retrieval. Topic age was not randomly assigned, and training coverage, reasoning resources and difficulty were not controlled. Consequently, observed differences describe these conditions and questions rather than a causal effect of information age. The answer to one question under one condition is the scoring unit. Statistical comparisons preserve question or matched-pair correspondence.

### 3.2 Question bank and reference information

We reused the fixed RMT-CS-v2 bank of 40 applied questions, identified as V2Q01–V2Q40. Twenty concern established concepts documented before 2020. Twenty concern features first publicly available in 2025, within the originally specified 2025–2026 eligibility window. Documented public previews were eligible. Python, PostgreSQL, TypeScript, Node.js and Git each contribute four established and four recent questions. Twenty pairs connect related tasks within ecosystems. Pairing supports structural comparability, although equal difficulty has not been independently established.

Questions require application, interpretation or diagnosis and contain three assessable parts. Version-specific manuals and release notes provide three binary reference checkpoints per question. Source identifiers, release evidence, expected information and rating explanations are retained in the archive. Questions without an authoritative solution or clear version boundary were excluded during instrument construction. This purposive quota sample covers selected technical tasks rather than a probability sample of computer science knowledge. The bank and its original results were already known when the supplement was designed, and source selection was informed by the instrument.

### 3.3 Archived response collection

The archived conditions are labelled GPT-6 Luna with Medium reasoning, Sonnet 5.5 with Medium reasoning, and Gemini 3.8 Flash. These labels were reported from the interfaces used by the students. Backend identities, account tiers, exact generation times and every interface setting were not independently verified. The prescribed collection procedure used four fixed ten-question blocks per condition, with a fresh chat for each block. Each block contained five questions from each topic group and two from each ecosystem. Paired questions occurred in different blocks.

The common instruction requested concise English answers to all three parts using existing knowledge, with no search, retrieval or code execution. Reference keys were withheld. Archived pasted responses document the delivered text, while compliance with chat resets and tool restrictions remains uncertain. A mistakenly supplied question prompt for Gemini's final block was excluded and replaced by the genuine supplied answers. The completed archive contains all 120 unique condition–question records. Original wording was preserved, and transport-format cleanup did not repair factual content. No pre-collection Moodle protocol submission was made for this stage.

### 3.4 Supplementary conditions and implementation

The simple baseline retrieves the three chunks with the largest number of distinct non-stopword query tokens in common, using lowercase ASCII alphanumeric and underscore tokenization. Ties are resolved by chunk identifier. It returns attributed passages verbatim. The model baseline uses the fixed MLX four-bit conversion of Qwen2.5-Coder-3B-Instruct [26], revision 3dd939c621c08e5753d5b89f35a2642cd83b98ca. This code-specialized model was feasible on the available 8 GB Apple Silicon computer. Its selection provides a practical local comparator, with no claim that it matches the capacity of the archived commercial systems.

Following the general retrieval-augmented approach [19], RAG uses exactly the same local model with three BM25-ranked documentation chunks. BM25 parameters are k1 = 1.5 and b = 0.75, with positive Robertson inverse document frequency. The corpus comprises 56 archived source URLs and 1552 frozen chunks of 180 whitespace-separated words, using a 140-word stride. Retrieval uses the question text without reference checkpoints or per-question filtering by answer-key source identifiers. The simple and RAG conditions share the corpus but use different ranking methods. Their contrast therefore combines generation and retrieval differences. The model–RAG contrast holds model weights and decoding settings constant while adding retrieved context.

Both generated conditions use a fresh context per question, seed 17, greedy decoding at temperature zero and a maximum of 192 generated tokens. Top-p was set to 0.95 but is inactive under greedy selection. Model and RAG calls were interleaved, alternating their order. The instruction requests direct answers, uncertainty where necessary and no external tools. RAG additionally supplies attributed documentation and asks the model to check versions. The recorded environment is macOS 26.3 on arm64, Python 3.12.14, MLX 0.32.4 and mlx-lm 0.32.2. Exact prompts, software requirements, timings, token counts and outputs are retained.

A prepared three-seed plan was reduced to one deterministic pass before the first supplementary output. The frozen manifest is timestamped 8 November 2026 at 14:58:08 UTC, preceding the first record at 14:58:48 UTC. The last record was completed at 15:12:12 UTC. The protocol history records this amendment and the absence of a Moodle upload. There were 40 outputs per condition, without retries for low-scoring answers. Source hashes allow the frozen corpus and generation scripts to be checked.

### 3.5 Outcomes and scoring

Primary strict accuracy is the proportion satisfying all three checkpoints without a material additional factual error. Partial responses satisfy one or two checkpoints, or all three with a material added error. Incorrect responses contain substantive content but satisfy no checkpoints. Abstention and missing outputs are recorded separately. The original analysis uses observed answers, while supplementary operational accuracy uses all planned questions, counting missing outputs as failures. Both denominators equal 40 per condition in the completed data. Secondary outcomes include checkpoint points, category counts, latency and retrieved reference-source coverage.

The same explicit-content rubric applies to extracted passages and generated answers. Relevant text receives credit when it directly supplies the required information. Ratings are AI-assisted source-key judgments with checkpoint decisions and reasons. Independent human-rater agreement was not measured. Sensitivity analysis removes the additional-error penalty and counts all responses meeting three checkpoints. Error coding records API/configuration, release/platform, added-claim, omission and type-precision issues, with an additional residual category in the supplement. Checkpoints within an answer are dependent and are not treated as independent trials.

### 3.6 Statistical analysis and reproducibility

We report counts, percentages and absolute differences in percentage points. Supplementary accuracy uses 95% Wilson intervals. The manuscript also applies the same Wilson calculation to original overall proportions as a descriptive uncertainty summary. Exact empirical paired-bootstrap intervals resample 20 topic pairs or 40 matched questions, depending on the comparison. These pointwise intervals are unadjusted for multiplicity. Original one-sided exact McNemar tests were added retrospectively and form a historical family of three Holm-adjusted tests [27]. The supplementary family contains three two-sided method comparisons and two one-sided established–recent comparisons. Significance requires adjusted p < 0.05 and the hypothesised direction.

Retrospective robustness checks resample four pairs within each ecosystem and repeat original topic comparisons while excluding each ecosystem in turn. Independence of questions or pairs remains an approximation because ecosystems and original prompt blocks may induce dependence. Median and interquartile latency summaries describe measured calls, excluding model loading. Each condition has one response per item, so across-run standard deviations are unavailable. All inference is exploratory for this reused question bank. Offline scripts validate input hashes, completeness, statistics and figure outputs. The study uses constructed technical questions and model responses, with no recruited human participants. Public documentation attribution is preserved, and AI assistance in rating, analysis and writing is disclosed.

## 4 Results

### 4.1 Completeness and original accuracy

The archived dataset contains 120 unique answers across 40 questions and three conditions, with no missing records or abstentions. Overall, 101 answers were fully correct and 19 were partial, yielding 84.2% strict accuracy. The checkpoint total was 344/360, or 95.6%. The difference between these measures reflects credit for individual correct facts within responses that did not satisfy the complete-answer criterion. The aggregate combines repeated evaluations of the same questions and is reported descriptively.

Table 2 presents original overall accuracy with descriptive Wilson intervals, topic-specific counts and checkpoint totals. Sonnet recorded the highest observed total at 36/40, followed by GPT at 35/40 and Gemini at 30/40. The one-answer difference between Sonnet and GPT is small relative to the uncertainty associated with this sample. These totals do not establish a general ordering of the models. Figure 1 displays established and recent accuracy separately, retaining the equal denominator of 20 questions per group.

All three original conditions performed better on established questions. GPT obtained 20/20 established and 15/20 recent answers, Sonnet 19/20 and 17/20, and Gemini 18/20 and 12/20. Combined counts were 57/60 and 44/60. The largest observed within-condition gap was 30 percentage points for Gemini, followed by 25 for GPT and 10 for Sonnet. The repeated-question and purposive-sampling structure limits population-level interpretation of these descriptive differences.

### 4.2 Paired original comparisons

Table 3 reports the original paired comparisons. GPT had five pairs correct only on the established item and none correct only on the recent item. Sonnet had two and zero, while Gemini had seven and one. The one-sided raw p-values were 0.0312, 0.2500 and 0.0352 respectively. After Holm adjustment, the values were 0.0938, 0.2500 and 0.0938. None met the 0.05 criterion. The observations support the expected direction descriptively, while the adjusted tests do not establish statistical significance.

Figure 2 shows pointwise paired-bootstrap intervals for the gaps. The intervals were 10–45 percentage points for GPT, 0–25 for Sonnet and 5–55 for Gemini. These unadjusted intervals address individual contrasts, whereas the reported Holm decisions control a family of tests. Consequently, excluding zero in an individual interval does not override the multiplicity-adjusted test result. The estimates remain conditional on the question bank and the approximate independence assumptions.

### 4.3 Supplementary accuracy and comparisons

All 120 planned supplementary outputs were produced and explicitly rated. Keyword extraction and the local model each achieved 4/40 fully correct outputs, or 10.0%, with Wilson intervals of 4.0–23.1%. RAG achieved 6/40, or 15.0%, with an interval of 7.1–29.1%. Table 4 reports these estimates and the corresponding checkpoint totals of 52/120, 44/120 and 65/120. The remaining category counts were 23 partial and 13 incorrect for extraction, 25 and 11 for the model, and 28 and 6 for RAG.

Figure 3 presents supplementary accuracy by topic. Extraction scored 2/20 in both groups. The model scored 4/20 established and 0/20 recent, while RAG scored 2/20 established and 4/20 recent. The observed topic direction therefore differed across the supplementary conditions. RAG's recent-topic advantage in this sample does not reproduce the original three conditions' established-topic advantage.

Table 5 contains all five supplementary comparisons. RAG exceeded each baseline by five percentage points overall. Its paired interval against the model was −7.5 to 17.5 points, and against extraction it was −7.5 to 20.0 points. All three between-method adjusted p-values were 1.0000. The model's established–recent gap was 20 points, with adjusted p = 0.3125. RAG's gap was −10 points, with adjusted p = 1.0000 for the directional established-topic test. These results provide insufficient evidence for the specified supplementary hypotheses at the adjusted threshold.

### 4.4 Sensitivity and error evidence

Table 6 compares strict and checkpoint-only scoring. The original total increased from 101/120 to 106/120 when additional-error penalties were ignored. Sonnet increased from 36 to 39 fully satisfied responses and Gemini from 30 to 32, while GPT remained at 35. In the supplement, extraction and the model remained at four, while RAG increased from six to nine. This increase identifies three RAG outputs that supplied the required facts but also contained material errors.

The original 19 error cases comprised seven API/configuration issues, five release/platform issues, five added-claim errors, one omission and one type-precision error. All 106 supplementary outputs below full correctness are retained in the error-case file. On V2Q40, the model named third-party zstandard when the question required Python 3.14's standard-library compression.zstd. RAG supplied the required module and compression/decompression functions, improving the recorded score from 1/3 to 3/3. On V2Q01, RAG still incorrectly asserted string-enum reverse mapping despite retrieving TypeScript documentation, receiving 1/3. These cases illustrate both successful and unsuccessful use of retrieved evidence.

### 4.5 Robustness and computational observations

Excluding one ecosystem at a time left all original established–recent gaps positive. Their ranges were 18.75–31.25 points for GPT, 6.25–12.50 for Sonnet and 12.50–43.75 for Gemini. Ecosystem-stratified interval estimates were 10–40, 0–25 and 15–45 points respectively. These retrospective diagnostics preserve ecosystem composition but do not model dependence caused by shared prompt blocks. They supplement the primary comparisons without creating further significance claims.

Table 7 reports supplementary latency and retrieval coverage. Median response-processing times were 0.0035 seconds for extraction, 6.8566 for the model and 11.8495 for RAG. Model loading took 2.33 seconds separately. Reference-source identifiers appeared among retrieved passages for 32/40 extraction questions and 38/40 RAG questions. Source overlap measures retrieval coverage rather than passage sufficiency. Eight model outputs and five RAG outputs reached the 192-token cap, which may limit completeness. Offline verification reproduced the 22 historical CSV/SVG files and the manuscript-specific exports from the saved evidence.

## 5 Discussion

The main research question asks how factual accuracy differs between established computer science concepts and recently introduced software features when selected assistant conditions are instructed to answer without external search. All three archived interface conditions showed higher complete-answer accuracy on the established group. The observed gaps were 25 percentage points for GPT, 10 points for Sonnet and 30 points for Gemini. This directional consistency is informative for the selected bank: questions about software releases, API details and version boundaries demanded greater caution than stable, long-documented concepts. It does not prove that the age of a feature caused an error. Difficulty, documentation prevalence, interface changes and the models’ unknown exposure to particular releases may all contribute to the observed differences.
Statistical evidence should be interpreted separately from the descriptive gaps. The analysis used twenty paired tasks per condition and one-sided exact McNemar comparisons. Once the family of three tests was adjusted using Holm’s procedure, p-values were 0.0938, 0.2500 and 0.0938. No comparison crossed the retrospective exploratory 0.05 threshold. Accordingly, the direction of the observed differences is supported in this small archive, whereas a population-level age effect is not established. Likewise, the overall counts of 35/40, 36/40 and 30/40 describe recorded ChatGPT, Claude and Gemini interface conditions rather than a rigorously controlled ranking of independently identified backend models. The one-answer difference between the first two conditions offers particularly little basis for claims of superiority.
The distinction between whole-answer accuracy and checkpoint accuracy matters for actual software work. Across original answers, 101/120 were fully correct, yet 344/360 individual checkpoints were satisfied. An explanation can therefore contain several valid statements while remaining unsafe to follow uncritically because it omits one requested qualification or includes a material extra claim. The error audit found issues involving API or configuration identifiers, release boundaries, unsupported added advice, omitted details and type precision. A practitioner relying on an answer to select a Python module, interpret a Git option or update a TypeScript type can be affected by one wrong version-specific detail despite otherwise fluent exposition. The study consequently treats complete, error-free three-part responses as its primary outcome and checkpoint totals as a complementary diagnostic measure.
The related literature helps contextualize these patterns without supplying a directly comparable effect size. Kabir et al. [1] demonstrate that technical answers to Stack Overflow questions can contain overlooked mistakes; their unit of analysis and earlier system differ from this applied version-aware benchmark. Kandpal et al. [4] show how long-tail factual knowledge relates to pretraining coverage, suggesting one mechanism by which less widely documented facts may be difficult. However, rarity and recent release date are different attributes, so that work cannot establish recency as a cause here. FreshLLMs by Vu et al. [6] investigates fast-changing factual knowledge and search support, but does not evaluate these five software ecosystems with matched scenario pairs. Wang et al. [5] studies deprecated API use in code completions; its findings reinforce attention to exact library versions but concern generated code rather than short explanatory answers. Our contribution is the transparent combination of temporal eligibility rules, official version-specific keys, three-checkpoint assessment and explicit uncertainty, not a claim to have invented factuality benchmarking.
The supplementary experiment examines documentation as a separate, modest intervention. Keyword extraction and Qwen2.5-Coder-3B-Instruct without documents each achieved 4/40 fully correct responses, whereas the same local Qwen condition with BM25-retrieved official passages achieved 6/40. The latter is an observed five-percentage-point gain, but all three between-method Holm-adjusted p-values were 1.0. It would therefore be inaccurate to call the improvement statistically demonstrated or to generalize it to all retrieval-augmented generation. The Qwen-only condition produced 4/20 established and 0/20 recent successes, whereas Qwen with retrieval produced 2/20 established and 4/20 recent. Consequently, the original established-topic advantage does not hold uniformly across the additional local conditions.
Individual examples illustrate both the value and the limits of documents. On item V2Q40, the closed-book model supplied zstandard where the required identifier was compression.zstd; with BM25 passages, its response met all three checkpoints rather than only one. On V2Q01, however, the retrieved-document condition still described a reverse mapping for a string enum incorrectly. Retrieved source presence is not the same as correct interpretation. The local keyword baseline also extracts attributed text rather than generating the same answer form as Qwen, so its task behavior is not fully comparable; the controlled Qwen-versus-Qwen-plus-documents contrast is more useful for assessing this pipeline.
Several validity threats constrain these interpretations. The bank contains only forty purposively selected questions and twenty approximate task pairs; equal difficulty was not independently established. Questions are clustered within five ecosystems and four original prompt blocks, so simple item-level independence assumptions are questionable. The historical model settings, actual collection timestamps, backend identifiers and compliance with prescribed fresh chats and disabled tools were not independently observed. The family of inferential tests was specified retrospectively after original answers were known; these tests remain exploratory, and the original collection did not have a pre-run Moodle registration.
The supplementary evaluation reused a bank already examined by the team and a document corpus chosen around that bank. It is not an unseen holdout. The Qwen comparison uses a relatively small four-bit model, one deterministic pass, a 192-token generation ceiling and a specific BM25 configuration, limiting transportability to other capacities and retrieval strategies. Some outputs reached the token limit. Ratings were AI-assisted and not accompanied by independent human inter-rater agreement; source-based checkpoints and preserved reasoning help auditability but cannot eliminate judgment error. Future replications should recruit independent assessors, record complete interface metadata, pre-register analyses, enlarge and diversify the question set, use previously unseen questions, and vary retrievers, context lengths and model families. The present practical recommendation is to verify version-sensitive technical claims against official documentation, while recognizing that simply supplying documents does not guarantee an accurate answer.

## 6 Conclusion

This study examined whether recorded AI assistant conditions answer established software concepts more accurately than recently introduced features under a prescribed no-search instruction. On the fixed 40-question, five-ecosystem benchmark, all three original conditions achieved higher complete-answer accuracy on established items. The observed differences were +25, +10 and +30 percentage points, respectively. However, the Holm-adjusted exact paired tests did not provide statistical support at the 0.05 level, so these results describe the archived questions and responses rather than a general causal recency effect or a definitive ranking of model providers.
The study contributes a transparent version-aware evaluation design: twenty task- and ecosystem-matched question pairs, official reference sources, three explicit checkpoints per response, a strict full-correctness rule, preserved records and reproducible saved-answer calculations. The primary experiment produced 101/120 fully correct responses and 344/360 achieved checkpoints, demonstrating why checkpoint coverage and complete-answer reliability should be reported separately.
A supplementary local comparison provided an initial test of documentation support. Keyword retrieval and Qwen without documents each achieved 4/40 fully correct answers, compared with 6/40 for Qwen augmented by BM25 passages. This five-point observed difference was not statistically established, and specific cases showed both repair of a module-identifier error and persistence of an incorrect claim despite retrieval.
Future research should use larger preregistered and unseen question collections, multiple independently rated responses, recorded model versions and settings, and controlled variation in model capacity and retrieval quality. Until such evidence is available, users should check recent software and API claims against authoritative release-specific documentation rather than treating fluent AI answers as sufficient verification.
